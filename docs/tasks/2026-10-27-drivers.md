# The driver system: interface, sidecar protocol, downloads and installation

## Problem Statement

A database client is only as useful as the databases it can reach, and the databases people reach are diverse: relational engines that differ in quoting, paging and transaction rules, document stores queried with their own shell language, key-value stores with no schema at all, and vendors whose client library is large, licensed, or only available for some platforms. Supporting each one inside a single build makes the application heavy and turns every new database into a release of the whole app. Loading vendor libraries into the process means a faulty driver can crash the client, and a driver written by someone else runs with the user's full privileges.

Users also need drivers they did not install with the app, without compiling anything and without trusting an arbitrary file they found online. Driver authors need one interface to implement, a way to test it against a real server, and confidence that what works in process also works when shipped separately. The application needs to describe the differences between databases as data, so that the Explorer, the editor and the agent features behave correctly without a branch per vendor.

## Solution

One driver interface covers three Families: relational, document and key-value. Each driver declares Capabilities and a Dialect, and the application derives its behaviour from those declarations instead of knowing vendors by name. Drivers are either Bundled into the binary or Sidecar executables that speak a versioned protocol over standard streams, so a third-party driver runs out of process, can be installed, updated and rolled back at runtime, and fails alone when it crashes.

A driver is written against an SDK, tested with a Conformance suite against a real database, and packaged from a template. The Driver Manager downloads published driver files from the project's releases, checks them against the release checksums, probes the handshake before activating anything, and lets the user review a manual archive before installing it. Every database in scope has its own documented behaviour, including the Mongo shell subset and the Elasticsearch console syntax that sqlr accepts.

## User Stories

1. As a PostgreSQL user, I want quoting, placeholders, paging and transaction statements handled correctly, so that generated SQL is accepted by the server.
2. As a MySQL or MariaDB user, I want the right identifier quoting and limit syntax, so that the Explorer and the editor work without me adjusting anything.
3. As a SQLite user, I want the client to rebuild a table where SQLite cannot alter it in place, so that editing a column definition still works.
4. As a SQL Server user, I want the dialect's paging and transaction behaviour, so that results and scripts behave as on the server.
5. As an Oracle user, I want the dialect and object behaviour of the server, so that browsing and editing follow its rules.
6. As a Snowflake user, I want its dialect and its unsupported operations hidden rather than failing, so that the interface only offers what the account can do.
7. As a MongoDB user, I want to type familiar shell statements and see their results, so that I can work without learning a different query language.
8. As a MongoDB user, I want the supported shell subset documented, so that I know which statements are accepted before I rely on them.
9. As a MongoDB user, I want collections opened as JSON documents with paging and indexes, so that document browsing feels native.
10. As an Elasticsearch user, I want to write requests in the console syntax I already know, so that I can explore indices without a second tool.
11. As a Redis user, I want keys scanned rather than listed with a blocking command, so that browsing a large database does not stall the server.
12. As a Redis user, I want editing and command execution to respect read-only mode, so that a production connection stays safe.
13. As a SAP HANA user, I want to install its driver from the Driver Manager, so that I do not need a build of my own.
14. As a DuckDB user, I want an embedded analytical engine reachable like any other database, so that I can query local files in the same client.
15. As a user with a JDBC-only database, I want a bridge that runs the vendor's JDBC driver, so that I can reach databases sqlr has no native driver for.
16. As a user installing a driver, I want to see its name, publisher, version, checksum, executable and capabilities before it is activated, so that I know what I am trusting.
17. As a user downloading a driver, I want the download checked against the release's published checksums and refused if it differs, so that a corrupted or replaced file never runs.
18. As a user, I want a failed install to leave nothing behind and to keep my current version working, so that trying a driver cannot break a working setup.
19. As a user, I want to keep several versions of a driver installed and switch between them, so that I can roll back an update that misbehaves.
20. As a user, I want a crash in a third-party driver to close only that driver's connections, so that my other work survives.
21. As a user, I want a restarted driver to reconnect, so that a crash costs me one reconnect and not a restart of the app.
22. As a user, I want a driver that never answers to be shut down after an idle period, so that unused processes do not linger.
23. As a user, I want the connection form built from the driver's manifest, so that each driver asks for exactly the fields it needs and marks secrets as secrets.
24. As a user, I want field validation before connecting, so that I see a wrong port or a missing file before a connection attempt.
25. As a user, I want cancelling a query to reach the server where the driver supports it, and to stop locally where it does not, so that cancel always does something.
26. As a driver author, I want one interface with operations grouped by Family, so that I implement only what my database offers.
27. As a driver author, I want to declare capabilities and an object-editing descriptor, so that the interface hides what I cannot do instead of failing at runtime.
28. As a driver author, I want the Dialect to be data exchanged over the protocol, so that the host can classify statements and generate SQL without calling into my process.
29. As a driver author, I want the same chunk format in process and over the protocol, so that my driver needs no transcoding layer.
30. As a driver author, I want an SDK that re-exports what I need and runs my driver as a sidecar, so that a working driver is a small amount of code.
31. As a driver author, I want a template that builds, installs and connects, so that I start from something that already works.
32. As a driver author, I want a Conformance suite to run against a real database, so that I know my driver behaves like the bundled ones.
33. As a driver author, I want clear rules for packaging and versioning, so that my driver can be installed and updated like the official ones.
34. As a maintainer, I want the protocol versioned with an explicit major check, so that old and new drivers fail with a clear message instead of misbehaving.
35. As a maintainer, I want the wire format specified byte by byte, so that drivers in other languages can implement it.
36. As a security-conscious user, I want downloads restricted to the project's release hosts and to size limits, so that a driver cannot pull from an arbitrary location or exhaust memory.
37. As a security-conscious user, I want archives rejected when they contain paths outside the install directory, so that unpacking cannot write elsewhere.
38. As a contributor, I want the protocol and chunk decoders fuzzed, so that malformed input from a driver cannot crash the client.
39. As a contributor, I want the manifest and the Dialect to be the only places a vendor is named, so that adding a database does not scatter conditionals through the app.
40. As an agent-connected user, I want driver capabilities reported to the agent host, so that tools offered to an agent match what the connection can actually do.

## Implementation Decisions

- Core defines the driver contract: identity and manifest, connect and ping, browsing, cancellation, family views for relational, document and key-value connections, database name and schema path, and switching database. Relational operations are execute with and without parameters, describe, explain, DDL, object references, introspection, administration, notices, origin checks, dialect and catalog. Document operations are run, split, replace, insert and delete a document, view detection, indexes, target text, node target, classification and read-only. Key-value operations are scan, key information, paging, edit, command, command blocks, classification, database list and read-only.
- Capabilities cover transactions, server cancel, editable results, explain, multiple result sets, tabular query, schemas, SSH tunnels and dump. Object editing is a descriptor with the kinds that can be created, altered, dropped and renamed, whether DDL is transactional, column types, comments and column ordering. The interface and the host read these descriptors rather than matching driver names.
- The Dialect is a data description: identifier quoting, select-all, syntax details, defaults, placeholder style, begin, commit and rollback statements, read-only statements, transactional DDL, error-aborts-transaction, error and destructive classification, statement wrapping, upsert, explain specification and DDL generation with placements for scripts that run in a transaction, alone, or only on cleanup.
- The manifest carries id, display name, Family, capabilities, the form fields with type, group, secret and free-form flags, the dialect id, URL schemes, default port and the object-editing descriptor. Fields of type text, port, password, boolean, file, choice and number are rendered by the form; validation rules run before connect; secret values are excluded from logs, diagnostics and connection files.
- Bundled drivers connect through their native client libraries and provide their own dialect, introspection, administration and DDL generation. Each has documented behaviour for browsing shapes, statement classification and the operations it cannot support.
- The document driver accepts a Mongo shell subset parsed by an interpreter in core: statements and their arguments, literals, database-level statements, classification by command, and errors with the offending text. The host renders documents as JSON, pages them, shows indexes and lets the user administer indexes; no JavaScript engine is involved.
- The key-value driver implements scan-based browsing with paging, key information, editing, single commands and command blocks, database selection and read-only enforcement. It never uses a blocking key listing for browsing.
- The sidecar protocol is versioned 1.0.0. Frames are length-prefixed with a four-byte big-endian length including a nine-byte header, a one-byte payload type, an eight-byte request id and the payload, capped at 64 MiB. Payload types are control messages in MessagePack with named fields, result chunks, reserved document chunks and log lines.
- The sidecar client owns request ids, one writer per process, pending replies, stream registries and cancellation. The server loop reads frames, dispatches by message name, streams results and answers errors with a driver error kind, message, position and hint.
- Handshake exchanges protocol and driver versions, rejects a different major version, and times out after ten seconds. Idle processes shut down after a configurable period. Cancellation gets a grace period, and shutdown waits briefly for the process to exit before killing it.
- The protocol serves relational drivers in version 1; document chunk encoding is defined and reserved for a later major version.
- Result chunks are columnar: a version byte, varint counts, column metadata (name, type name, physical kind, display hint, origin), a validity bitmap where a set bit means not null, and per-kind values into a byte arena. Kinds are boolean, integer, float, text, bytes and mixed; hints distinguish numbers, decimals, temporals, intervals, JSON, XML, UUID, arrays, geometry and binary. A chunk without columns carries a row count up to a fixed limit. The decoder rejects unknown versions and malformed layouts.
- The SDK re-exports the driver API and provides a run entry point that serves a driver over the protocol. The template produces a driver crate that builds, connects and passes the Conformance suite skeleton.
- The Conformance suite drives a real database through the interface: connect, ping, browse, execute and streaming, fetch more, affected rows, syntax errors, quoting round trip, cancel, type matrix and describe for editing. It takes a target that supplies setup rows, a slow statement and type cases, and checks the declared capabilities.
- The registry models a driver index with id, version, platform, URL, checksum and signature. It verifies a minisign signature over the index and over each artifact when a signed index is used, and a SHA-256 checksum always. The downloader allows HTTPS, test HTTP and local file mirrors, follows redirects only to the same host or from the project's GitHub host to its content host for at most five hops, and enforces size caps on index, artifact and unpacked content.
- Archive extraction refuses absolute paths, parent traversal, links outside the archive and unsupported entry types. Installation goes through a staging directory, requires a driver manifest of bounded size, probes the sidecar handshake before activation, and only then moves the version into place and points the active marker at it. Failed installs remove staging.
- Release downloads read the release's checksum file, find the asset for the platform, download it, compare the checksum and only then unpack. Driver files are named by driver id, version and platform. Manual installs surface the review data: id, version, executable, checksum, capabilities and the source, requiring acceptance before install.
- Install layout keeps one directory per driver and version with manifest, normalized manifest copy and executable, plus an active pointer. Several versions coexist; activation and rollback switch the pointer.
- The engine owns the driver catalog, launches sidecars on demand, tracks their processes, restarts them after a crash, shuts them down when idle and runs install, update and removal off the UI thread. Drivers can be reached only through the interface, so bundled and sidecar drivers are interchangeable.
- The application registers bundled drivers at startup and provides the Driver Manager, install and review dialogs and progress reporting. Widgets render the manifest-driven connection form and the Driver Manager and return actions instead of calling the registry.

## Testing Decisions

- Driver seam: the Conformance suite run by every relational driver against the shared database services, both in process and through a sidecar process. Prior art: the PostgreSQL and MySQL conformance suites, the DuckDB native and sidecar suites, and the HANA live suite that is ignored by default.
- Protocol seam: frame encoding and decoding, malformed and oversized frames, handshake version negotiation and timeouts, streaming with fetch and close, cancellation, idle shutdown and crash handling, driven between the protocol server and client and through the engine with a sidecar driver. Prior art: the sidecar protocol and process tests and the engine's sidecar integration tests.
- Chunk seam: encode and decode round trips for every kind and hint, validity bitmaps, mixed columns, empty chunks and truncated input. Prior art: the chunk and document chunk unit tests.
- Registry seam: release downloads with local mirrors, checksum mismatch, missing platform asset, redirect policy, size caps, archive traversal and links, signed index acceptance and refusal, version activation and rollback, and manual review. Prior art: the registry install and security test suites.
- Security: fuzz targets for the frame decoder and the chunk decoder, plus seeded random mutations of valid messages. Prior art: the existing fuzz targets.
- Manifest and form: validation rules, secret redaction, dialect round trip over the wire and the form fields produced for each bundled driver. Prior art: the manifest and driver property tests.
- Shell parsers: the Mongo shell subset and the Elasticsearch console parser tested against accepted and rejected statements and error positions.

## Acceptance Criteria

- [x] One driver interface serves relational, document and key-value databases, with operations grouped per Family.
- [x] Capabilities and the object-editing descriptor are declared per driver and drive the Explorer, editors and agent tools.
- [x] The Dialect describes quoting, select-all, placeholders, paging, transaction and read-only statements, classification, wrapping, upsert, Explain and DDL generation.
- [x] Identifier quoting always goes through the Dialect, and catalog statements are parameterized.
- [x] The manifest declares identity, Family, fields, URL schemes, default port and object editing, and its form schema renders the connection form.
- [x] Field validation runs before a connection attempt and reports the offending field.
- [x] Secret field values are excluded from logs, diagnostics and connection files.
- [x] Bundled drivers cover PostgreSQL, MySQL and MariaDB, SQLite, SQL Server, Oracle, Snowflake, MongoDB, Elasticsearch and Redis.
- [x] PostgreSQL, MySQL, MariaDB, SQLite, SQL Server, Oracle, Snowflake, MongoDB, Elasticsearch and Redis have their documented per-database behaviour, including SQLite's table rebuild, Mongo shell statements and Elasticsearch console syntax.
- [x] The Mongo shell subset is parsed without a JavaScript engine, with database-level statements and documented errors.
- [x] Redis browsing uses scan with paging rather than a blocking key listing.
- [x] A driver can be installed, launched and used without rebuilding the application.
- [x] Sidecar drivers run out of process, and a crash fails only their connections.
- [x] A crashed driver can be restarted and its connections reconnected.
- [x] A sidecar that stays idle is shut down after the configured idle period.
- [x] Protocol frames are length-prefixed, capped at 64 MiB, carry a request id and a payload type, and reject unknown or malformed input.
- [x] The handshake checks the protocol major version, has a time limit and reports a readable mismatch.
- [x] Every request and response in protocol 1.0.0 is implemented as specified, including streams, cancellation and notices.
- [x] Result chunks use a versioned columnar encoding with validity bitmaps, display hints and varint lengths, and are identical in process and over the protocol.
- [x] Document chunk encoding is specified and reserved for a later protocol major version.
- [x] The Dialect crosses the protocol as data so the host classifies statements and generates SQL without calling the driver process.
- [x] The SDK re-exports the driver API and runs a driver as a sidecar.
- [x] The template produces a driver that builds, connects and has the Conformance suite wired in.
- [x] The Conformance suite runs against real databases for every relational driver, in process and through a sidecar.
- [x] Release downloads verify the asset against the release's SHA-256 list before unpacking.
- [x] A signed registry index and its artifacts are verified against the project key before installation.
- [x] Downloads are restricted to the project's release hosts, follow only allowed redirects and enforce size limits.
- [x] Archive extraction rejects absolute paths, parent traversal, escaping links and unsupported entries.
- [x] An install is staged, its manifest bounded and its handshake probed, and nothing is activated unless every check passed.
- [x] Failed installs leave no files behind and keep the previous active version working.
- [x] Several versions of a driver coexist, and activation and rollback switch the active one.
- [x] Manual driver archives are shown for review with identity, version, checksum, executable and capabilities before install.
- [x] The Driver Manager shows installed drivers, their versions and their state, and offers install, update, rollback and removal.
- [x] The sidecar frame decoder and the chunk decoder have fuzz targets.
- [ ] Release downloads are also signature-verified, so that a compromised release host cannot substitute a checksum file. Only the registry index path uses signatures today.
- [ ] The Conformance suite and the live driver tests run in CI against real servers for every driver.
- [ ] The SAP HANA driver and the JDBC bridge presets are verified against real servers; their tests exist but are ignored or incomplete.
- [ ] DuckDB returns every column type without manual casts; `TIME_NS` needs an explicit cast.
- [ ] Third-party drivers run inside an OS sandbox that limits their file and network access.

## Out of Scope

- Redis Cluster and Sentinel topologies.
- Additional JDBC presets beyond the documented ones.
- Code signing and notarization of driver executables.
- Hot-reloading a driver into the running process: sidecars replace this.
- Drivers written in languages other than Rust, beyond the protocol specification.

## Further Notes

This task records retroactively the work that built the area as it exists today. The unticked criteria are the known gaps: release downloads rely on HTTPS and `SHA256SUMS.txt` without a signature, the signed index path is used by local mirrors and tests rather than by the Driver Manager; driver live suites need the shared services and are not part of CI; HANA and the JDBC bridge presets are documented but not exercised against real servers; DuckDB's nanosecond time column requires a cast; drivers are not sandboxed beyond running out of process. The earlier design document mentioned signature verification of release downloads and a driver index for the public path; the code delivers checksums there and signatures only for the registry index, so the spec records the implemented behaviour.
