## Findings

### Session, commit modes and the transaction state machine

#### A cancelled fetch inside a transaction left it looking open

- Where: `crates/sqlr-engine/src/engine.rs` (`fetch_pages`, `after_fetch_cancelled`)
- Problem: cancelling a fetch inside an open transaction ended the Result `Cancelled`
  but never reconciled the transaction state. On a dialect where an error aborts the
  transaction (PostgreSQL), the cancellation had aborted it too, yet the toolbar kept
  offering Commit and savepoints, and only a later statement failed with "current
  transaction is aborted". The driver-returned-cancel path tried to undo the statement
  through its savepoint instead of marking the transaction failed, contrary to
  `docs/specs/query-execution.md` ("Failed remains … after a failed or cancelled fetch
  inside a user transaction").
- Test: `crates/sqlr-engine/tests/tx.rs`, "a_cancelled_fetch_inside_a_transaction_leaves_only_rollback"
- Fix: a cancelled fetch (`PageEnd::Stopped`, or an `ErrorKind::Cancelled` from the
  driver) now reconciles the transaction through `after_fetch_cancelled`, which moves an
  open transaction to Failed on a dialect where an error aborts it. Other failures keep
  the statement-savepoint undo behaviour.

#### MySQL/MariaDB: a typed `BEGIN` inside an open transaction implicitly commits (to confirm)

- Where: `crates/sqlr-engine/src/tx.rs` (`TxState::after_success`, `TxVerb::Begin`)
- Behaviour: when the tracked transaction is already open and the dialect does not nest
  `BEGIN`, a successful typed `BEGIN`/`START TRANSACTION` leaves the state untouched. On
  MySQL/MariaDB the server commits the pending transaction and starts a new one, so the
  engine keeps the old statement count, start time, `wrote` flag and savepoints.
- Why it might be a bug: the spec's decision says the toolbar and status bar always
  reflect the server's real state, including server quirks; the listed savepoints no
  longer exist and earlier work is already committed.
- Why it might be intended: the spec enumerates the supported transaction quirks and
  does not list implicit commit on `BEGIN`; adding it needs a new Dialect rule (and the
  sidecar wire form), so it is a product decision.

#### MySQL/MariaDB implicit commits around DDL are modelled too broadly (to confirm)

- Where: `crates/sqlr-core/src/classify.rs` (`is_schema_change`) and
  `crates/sqlr-engine/src/tx.rs` (`needs_begin`, `after_success`, `after_failure`)
- Behaviour: every schema-changing statement on a `ddl_commits` dialect closes the
  tracked transaction. MySQL does not implicitly commit for `CREATE/DROP TEMPORARY
  TABLE`, so the engine closes a transaction the server still holds; and it does
  implicitly commit for `ANALYZE`, `OPTIMIZE`, `REPAIR`, `LOCK TABLES`, `FLUSH` and
  `SET autocommit = 1`, which the classifier leaves as `Other`, so the engine keeps a
  transaction the server committed.
- Why it might be a bug: the tracked phase can disagree with the server in both
  directions.
- Why it might be intended: `docs/specs/query-execution.md` states the simple rule
  ("schema-changing statements … ends it with the warning"); implementing the real MySQL
  list changes what the spec describes and needs a dialect rule, so it is a product
  decision.

### Statement execution: single statements, errors, reconnect, DDL invalidation

#### A statement queued behind a connection-error reconnect failed "not connected"

- Where: `crates/sqlr-engine/src/engine.rs` (`execute`, the rebind block)
- Problem: every queued `Execute` carries the `SessionIo` captured at issue time. When an
  earlier statement hit a connection error, the engine replaced the session (reconnect
  after a read, or a failed session left for the next statement). A second statement
  already queued then found no session with its old I/O and ended `Failed("not
  connected")` even though the session had reconnected or was reconnecting. The same
  window opened when the idle pinger failed the session just before a queued run.
- Test: `crates/sqlr-engine/tests/engine.rs`,
  "a_queued_statement_runs_after_an_earlier_connection_error_reconnects"
- Fix: a queued command whose session was replaced now moves itself to the session's
  current connection (reopening a failed one) and requeues, keeping its place in the
  issue order, instead of failing. The rerun of the interrupted statement is dispatched
  before the old stream is released so a later queued statement cannot overtake it.

#### The connection-error retry judged only the first statement of a batch

- Where: `crates/sqlr-engine/src/engine.rs` (`run_statement`)
- Problem: the "run it again after a connection error" rule used `Stmt::of`, which
  classifies only the first statement. A batch whose first statement reads but which
  contains a later write (`SELECT 1` then `DELETE FROM t`) was therefore re-run on the
  new connection after a connection error, although the write may already have taken
  effect before the link dropped: a possible duplicate write.
- Test: `crates/sqlr-engine/tests/tx.rs`,
  "a_batch_with_a_hidden_write_is_not_run_again_after_a_connection_error"
- Fix: the retry now requires the whole script to classify as `Read`
  (`classify_script`), the same conservative view the confirmations and read-only checks
  already use.

#### One retried query showed two Operations, the first reporting success

- Where: `crates/sqlr-engine/src/engine.rs` (`handle`, `rerun_on_new_connection`) and
  `crates/sqlr-engine/src/operations.rs` (`resume_query`)
- Problem: the retried read is a second `Command::Execute`, which started a second Query
  Operation. The first attempt's Operation ended while the Result was still `Running` and
  was recorded `Done { ok: true }`, so the Operations panel showed a success plus a
  duplicate entry for one user query.
- Test: `crates/sqlr-engine/tests/operations.rs`, "a_retried_query_keeps_one_operation"
- Fix: an Execute that the engine moves to another connection is marked `resumed`; its
  handler resumes the existing Query Operation instead of creating one, and a command
  that hands the query on leaves the Operation Running until the final attempt settles it.

#### The reconnect note did not match the spec

- Where: `crates/sqlr-engine/src/engine.rs` (`rerun_on_new_connection`)
- Problem: the spec says the retried read's Messages say "Connection restored"; the code
  said "The connection was lost; reconnected and ran the statement again".
- Test: `crates/sqlr-engine/tests/tx.rs`, "a_read_on_a_dead_connection_runs_again_on_a_new_one"
- Fix: the message is now "Connection restored".

The reported catalog-invalidation false positive (`SELECT comment …` treated as DDL) did
not hold: `SqlSyntax::is_ddl` stops at the first significant token (the lexer callback
returns `false` after it), confirmed by "a_read_that_mentions_a_ddl_word_does_not_refresh_the_catalog".

### Cancellation, timeouts, idle ping and lost connections

#### A cancelled statement that reports a row count ended `Ready`, not `Cancelled`

- Where: `crates/sqlr-engine/src/engine.rs` (`run_statement`, the `Execution::Affected` arm)
- Problem: when a driver has no server cancel (Oracle) or the cancel lands after the
  statement already finished, the statement returns its affected-row count. The engine
  never looked at the cancel flag on that path and marked the Result `Ready` with "N rows
  affected", so a Stop was silently ignored. The spec says Oracle's statement runs to the
  end and then ends `Cancelled`.
- Test: `crates/sqlr-engine/tests/engine.rs`,
  "a_cancelled_statement_that_reports_rows_affected_ends_cancelled"
- Fix: the affected-row path checks the query's cancel flag before settling and ends the
  Result `Cancelled` (keeping the row count) when Stop was pressed.

#### Idle ping race (`not connected` on a queued run)

- Where: `crates/sqlr-engine/src/engine.rs` (`ping_idle_sessions`, `execute`)
- Problem: the pinger fails the session when a ping times out while a statement is
  already queued; that statement then failed `not connected` instead of reconnecting.
- Test: covered by the queued-statement rebind test above (same stale-I/O seam); the
  60-second idle window itself has no clock seam.
- Fix: the rebind described in the execution section recovers this case too.

#### SQLite cancel check and interrupt race

- Where: `crates/sqlr-driver-sqlite/src/worker.rs` (`interrupt`) and
  `crates/sqlr-driver-sqlite/src/execute.rs` (`Running::start`)
- Behaviour and fix: see the "Relational drivers: PostgreSQL and SQLite" section. The
  leaked-interrupt half turned out to be harmless (SQLite clears a pending interrupt when
  the next statement is prepared); the lost cancel is fixed there.

### Results: paging, cut short, close, memory budgets and spill

#### A fetch that failed or was cancelled never recorded its outcome or notes

- Where: `crates/sqlr-engine/src/engine.rs` (`finish_with`)
- Problem: `finish_with` added the outcome message and the transaction notes only the
  first time the Result left `Running`, which is the initial page. Every later
  `fetch_more`/`fetch_all` ran with `first == None`, so a failed fetch kept only the stale
  "N rows (more available)" line with no error, a cancelled fetch said nothing, and the
  "transaction failed: only Rollback is possible" / "transaction was lost" notes were
  dropped. The status bar and transaction state changed, but the Messages pane did not
  explain why.
- Test: `crates/sqlr-engine/tests/tx.rs`,
  "a_fetch_that_fails_inside_a_transaction_is_undone_alone" (now asserts the error line
  and the transaction note)
- Fix: the outcome and notes are also added when a later fetch settles the Result for
  good (`Failed`, `Cancelled`, or `Ready { more: false }`), not while it still has rows.

#### A refused statement still cut the previous result short

- Where: `crates/sqlr-engine/src/engine.rs` (`execute`, `run_statement`, `finish_with`)
- Problem: `execute` closed the previous stream before the new statement was validated
  and before any connection was chosen. A statement refused for a missing sibling
  database, an unsupported transaction, read-only mode or "a transaction is open on
  another database" therefore marked the previous Result cut short, unlike the spec's
  "when a later statement took its stream". The supersede mark set by `start_query`
  stayed on the earlier Result too, so its next `fetch_more` was cut.
- Test: `crates/sqlr-engine/tests/engine.rs`,
  "a_refused_statement_does_not_cut_the_previous_result_short"
- Fix: the previous stream is closed inside `run_statement`, after every local refusal
  and just before the first SQL runs; results now carry `took_stream`, and a query that
  never reached a connection clears the supersede marks it set on earlier results.

### Connection lifecycle, store, secrets, URL parsing and SSH

#### A store save reply for another connection was taken by the open dialog

- Where: `crates/sqlr-app/src/dialogs.rs` (`connection_save_ended`, `save_failed`,
  `saving_id`) and `crates/sqlr-app/src/app.rs` (`StoreReply::Saved` dispatch)
- Problem: `StoreReply::Saved` carries the connection id, but the dialog was matched only
  by "is saving". A save by an agent or `SetAgentAccess` for connection B arriving while
  the human dialog was saving A closed A's dialog on success; on failure it ran
  `save_failed(B)` on A's dialog, which rewrote the dialog's edited id to B while the
  form still held A, so the next Save upserted A's form over connection B.
- Test: `crates/sqlr-app/src/dialogs.rs`,
  "a_save_reply_is_matched_to_the_connection_the_dialog_saved"
- Fix: the dialog records the id it is saving (a fresh one for a new connection) and the
  app only applies a reply whose id matches; other replies leave it untouched.

#### A partial vault read discards the secrets already read (to confirm)

- Where: `crates/sqlr-engine/src/store.rs` (`connect_secrets`)
- Behaviour: the blocking read collects values in a vector and returns `Err` as soon as
  one `get` fails, dropping the values already read; the connect then proceeds with the
  given secrets and a notice.
- Why it might be a bug: the spec says a vault read failure "becomes a notice and the
  connect proceeds with what it has"; the values read before the failure are part of what
  it had.
- Why it might be intended: a failing vault normally fails every read (locked keychain),
  so the partial case is rare, and failing the whole read keeps the behaviour
  deterministic.

### Relational drivers: PostgreSQL and SQLite

#### PostgreSQL reported a server statement timeout as a user cancel

- Where: `crates/sqlr-driver-postgres/src/errors.rs` (`kind_for_sqlstate`)
- Problem: SQLSTATE `57014` was always `ErrorKind::Cancelled`. That state also covers
  `statement_timeout` ("canceling statement due to statement timeout"), so a query the
  server killed on time appeared as "cancelled" in the Result, the History and the logs
  (debug level), instead of a `Timeout`.
- Test: `crates/sqlr-driver-postgres/src/errors.rs` unit test
  "server_shutdown_and_termination_are_connection_errors" (now also checks the two
  `57014` messages)
- Fix: `57014` with "statement timeout" in its message maps to `Timeout`; user and
  administrator cancels stay `Cancelled`.

#### SQLite dropped a cancel that arrived while the statement was prepared

- Where: `crates/sqlr-driver-sqlite/src/execute.rs` (`run`)
- Problem: the worker's "a statement is stepping" flag was set only immediately before
  `raw_execute`/`fetch`, so `Worker::interrupt` did nothing for a cancel arriving during
  `prepare`, the parameter-count check or the binds. The statement then ran to the end,
  while the engine still settled the Result `Cancelled` because the query's cancel flag
  was set: the user was told a statement was cancelled while its writes committed.
- Test: no deterministic seam; closing the window needs the prepare phase to be slow,
  which the fake does not model. The driver test suite passes unchanged.
- Fix: the running guard is taken before `prepare` and covers the prepare, bind and
  execute phases; it is released only while the rows result waits for fetch commands
  (where the engine does not send cancels). SQLite clears a pending interrupt when the
  next statement is prepared, so releasing the guard before the fetch wait cannot leak
  into later work.
