## Findings

### Session, commit modes and the transaction state machine

#### A cancelled fetch inside a transaction left it looking open

- Where: `crates/sqlr-engine/src/engine.rs` (`fetch_pages`, `after_fetch_cancelled`)
- Problem: cancelling a fetch inside an open transaction ended the Result `Cancelled`
  but never reconciled the transaction state. On a dialect where an error aborts the
  transaction (PostgreSQL), the cancellation had aborted it too, yet the toolbar kept
  offering Commit and savepoints, and only a later statement failed with "current
  transaction is aborted". The driver-returned-cancel path tried to undo the statement
  through its savepoint instead of marking the transaction failed, contrary to
  `docs/specs/query-execution.md` ("Failed remains … after a failed or cancelled fetch
  inside a user transaction").
- Test: `crates/sqlr-engine/tests/tx.rs`, "a_cancelled_fetch_inside_a_transaction_leaves_only_rollback"
- Fix: a cancelled fetch (`PageEnd::Stopped`, or an `ErrorKind::Cancelled` from the
  driver) now reconciles the transaction through `after_fetch_cancelled`, which moves an
  open transaction to Failed on a dialect where an error aborts it. Other failures keep
  the statement-savepoint undo behaviour.

#### MySQL/MariaDB: a typed `BEGIN` inside an open transaction implicitly commits (to confirm)

- Where: `crates/sqlr-engine/src/tx.rs` (`TxState::after_success`, `TxVerb::Begin`)
- Behaviour: when the tracked transaction is already open and the dialect does not nest
  `BEGIN`, a successful typed `BEGIN`/`START TRANSACTION` leaves the state untouched. On
  MySQL/MariaDB the server commits the pending transaction and starts a new one, so the
  engine keeps the old statement count, start time, `wrote` flag and savepoints.
- Why it might be a bug: the spec's decision says the toolbar and status bar always
  reflect the server's real state, including server quirks; the listed savepoints no
  longer exist and earlier work is already committed.
- Why it might be intended: the spec enumerates the supported transaction quirks and
  does not list implicit commit on `BEGIN`; adding it needs a new Dialect rule (and the
  sidecar wire form), so it is a product decision.

#### MySQL/MariaDB implicit commits around DDL are modelled too broadly (to confirm)

- Where: `crates/sqlr-core/src/classify.rs` (`is_schema_change`) and
  `crates/sqlr-engine/src/tx.rs` (`needs_begin`, `after_success`, `after_failure`)
- Behaviour: every schema-changing statement on a `ddl_commits` dialect closes the
  tracked transaction. MySQL does not implicitly commit for `CREATE/DROP TEMPORARY
  TABLE`, so the engine closes a transaction the server still holds; and it does
  implicitly commit for `ANALYZE`, `OPTIMIZE`, `REPAIR`, `LOCK TABLES`, `FLUSH` and
  `SET autocommit = 1`, which the classifier leaves as `Other`, so the engine keeps a
  transaction the server committed.
- Why it might be a bug: the tracked phase can disagree with the server in both
  directions.
- Why it might be intended: `docs/specs/query-execution.md` states the simple rule
  ("schema-changing statements … ends it with the warning"); implementing the real MySQL
  list changes what the spec describes and needs a dialect rule, so it is a product
  decision.

### Statement execution: single statements, errors, reconnect, DDL invalidation

#### A statement queued behind a connection-error reconnect failed "not connected"

- Where: `crates/sqlr-engine/src/engine.rs` (`execute`, the rebind block)
- Problem: every queued `Execute` carries the `SessionIo` captured at issue time. When an
  earlier statement hit a connection error, the engine replaced the session (reconnect
  after a read, or a failed session left for the next statement). A second statement
  already queued then found no session with its old I/O and ended `Failed("not
  connected")` even though the session had reconnected or was reconnecting. The same
  window opened when the idle pinger failed the session just before a queued run.
- Test: `crates/sqlr-engine/tests/engine.rs`,
  "a_queued_statement_runs_after_an_earlier_connection_error_reconnects"
- Fix: a queued command whose session was replaced now moves itself to the session's
  current connection (reopening a failed one) and requeues, keeping its place in the
  issue order, instead of failing. The rerun of the interrupted statement is dispatched
  before the old stream is released so a later queued statement cannot overtake it.

#### The connection-error retry judged only the first statement of a batch

- Where: `crates/sqlr-engine/src/engine.rs` (`run_statement`)
- Problem: the "run it again after a connection error" rule used `Stmt::of`, which
  classifies only the first statement. A batch whose first statement reads but which
  contains a later write (`SELECT 1` then `DELETE FROM t`) was therefore re-run on the
  new connection after a connection error, although the write may already have taken
  effect before the link dropped: a possible duplicate write.
- Test: `crates/sqlr-engine/tests/tx.rs`,
  "a_batch_with_a_hidden_write_is_not_run_again_after_a_connection_error"
- Fix: the retry now requires the whole script to classify as `Read`
  (`classify_script`), the same conservative view the confirmations and read-only checks
  already use.

#### One retried query showed two Operations, the first reporting success

- Where: `crates/sqlr-engine/src/engine.rs` (`handle`, `rerun_on_new_connection`) and
  `crates/sqlr-engine/src/operations.rs` (`resume_query`)
- Problem: the retried read is a second `Command::Execute`, which started a second Query
  Operation. The first attempt's Operation ended while the Result was still `Running` and
  was recorded `Done { ok: true }`, so the Operations panel showed a success plus a
  duplicate entry for one user query.
- Test: `crates/sqlr-engine/tests/operations.rs`, "a_retried_query_keeps_one_operation"
- Fix: an Execute that the engine moves to another connection is marked `resumed`; its
  handler resumes the existing Query Operation instead of creating one, and a command
  that hands the query on leaves the Operation Running until the final attempt settles it.

#### The reconnect note did not match the spec

- Where: `crates/sqlr-engine/src/engine.rs` (`rerun_on_new_connection`)
- Problem: the spec says the retried read's Messages say "Connection restored"; the code
  said "The connection was lost; reconnected and ran the statement again".
- Test: `crates/sqlr-engine/tests/tx.rs`, "a_read_on_a_dead_connection_runs_again_on_a_new_one"
- Fix: the message is now "Connection restored".

The reported catalog-invalidation false positive (`SELECT comment …` treated as DDL) did
not hold: `SqlSyntax::is_ddl` stops at the first significant token (the lexer callback
returns `false` after it), confirmed by "a_read_that_mentions_a_ddl_word_does_not_refresh_the_catalog".

### Cancellation, timeouts, idle ping and lost connections

#### A cancelled statement that reports a row count ended `Ready`, not `Cancelled`

- Where: `crates/sqlr-engine/src/engine.rs` (`run_statement`, the `Execution::Affected` arm)
- Problem: when a driver has no server cancel (Oracle) or the cancel lands after the
  statement already finished, the statement returns its affected-row count. The engine
  never looked at the cancel flag on that path and marked the Result `Ready` with "N rows
  affected", so a Stop was silently ignored. The spec says Oracle's statement runs to the
  end and then ends `Cancelled`.
- Test: `crates/sqlr-engine/tests/engine.rs`,
  "a_cancelled_statement_that_reports_rows_affected_ends_cancelled"
- Fix: the affected-row path checks the query's cancel flag before settling and ends the
  Result `Cancelled` (keeping the row count) when Stop was pressed.

#### Idle ping race (`not connected` on a queued run)

- Where: `crates/sqlr-engine/src/engine.rs` (`ping_idle_sessions`, `execute`)
- Problem: the pinger fails the session when a ping times out while a statement is
  already queued; that statement then failed `not connected` instead of reconnecting.
- Test: covered by the queued-statement rebind test above (same stale-I/O seam); the
  60-second idle window itself has no clock seam.
- Fix: the rebind described in the execution section recovers this case too.

#### SQLite cancel check and interrupt race

- Where: `crates/sqlr-driver-sqlite/src/worker.rs` (`interrupt`) and
  `crates/sqlr-driver-sqlite/src/execute.rs` (`Running::start`)
- Behaviour and fix: see the "Relational drivers: PostgreSQL and SQLite" section. The
  leaked-interrupt half turned out to be harmless (SQLite clears a pending interrupt when
  the next statement is prepared); the lost cancel is fixed there.

### Results: paging, cut short, close, memory budgets and spill

#### A fetch that failed or was cancelled never recorded its outcome or notes

- Where: `crates/sqlr-engine/src/engine.rs` (`finish_with`)
- Problem: `finish_with` added the outcome message and the transaction notes only the
  first time the Result left `Running`, which is the initial page. Every later
  `fetch_more`/`fetch_all` ran with `first == None`, so a failed fetch kept only the stale
  "N rows (more available)" line with no error, a cancelled fetch said nothing, and the
  "transaction failed: only Rollback is possible" / "transaction was lost" notes were
  dropped. The status bar and transaction state changed, but the Messages pane did not
  explain why.
- Test: `crates/sqlr-engine/tests/tx.rs`,
  "a_fetch_that_fails_inside_a_transaction_is_undone_alone" (now asserts the error line
  and the transaction note)
- Fix: the outcome and notes are also added when a later fetch settles the Result for
  good (`Failed`, `Cancelled`, or `Ready { more: false }`), not while it still has rows.

#### A refused statement still cut the previous result short

- Where: `crates/sqlr-engine/src/engine.rs` (`execute`, `run_statement`, `finish_with`)
- Problem: `execute` closed the previous stream before the new statement was validated
  and before any connection was chosen. A statement refused for a missing sibling
  database, an unsupported transaction, read-only mode or "a transaction is open on
  another database" therefore marked the previous Result cut short, unlike the spec's
  "when a later statement took its stream". The supersede mark set by `start_query`
  stayed on the earlier Result too, so its next `fetch_more` was cut.
- Test: `crates/sqlr-engine/tests/engine.rs`,
  "a_refused_statement_does_not_cut_the_previous_result_short"
- Fix: the previous stream is closed inside `run_statement`, after every local refusal
  and just before the first SQL runs; results now carry `took_stream`, and a query that
  never reached a connection clears the supersede marks it set on earlier results.

### Connection lifecycle, store, secrets, URL parsing and SSH

#### A store save reply for another connection was taken by the open dialog

- Where: `crates/sqlr-app/src/dialogs.rs` (`connection_save_ended`, `save_failed`,
  `saving_id`) and `crates/sqlr-app/src/app.rs` (`StoreReply::Saved` dispatch)
- Problem: `StoreReply::Saved` carries the connection id, but the dialog was matched only
  by "is saving". A save by an agent or `SetAgentAccess` for connection B arriving while
  the human dialog was saving A closed A's dialog on success; on failure it ran
  `save_failed(B)` on A's dialog, which rewrote the dialog's edited id to B while the
  form still held A, so the next Save upserted A's form over connection B.
- Test: `crates/sqlr-app/src/dialogs.rs`,
  "a_save_reply_is_matched_to_the_connection_the_dialog_saved"
- Fix: the dialog records the id it is saving (a fresh one for a new connection) and the
  app only applies a reply whose id matches; other replies leave it untouched.

#### A partial vault read discards the secrets already read (to confirm)

- Where: `crates/sqlr-engine/src/store.rs` (`connect_secrets`)
- Behaviour: the blocking read collects values in a vector and returns `Err` as soon as
  one `get` fails, dropping the values already read; the connect then proceeds with the
  given secrets and a notice.
- Why it might be a bug: the spec says a vault read failure "becomes a notice and the
  connect proceeds with what it has"; the values read before the failure are part of what
  it had.
- Why it might be intended: a failing vault normally fails every read (locked keychain),
  so the partial case is rare, and failing the whole read keeps the behaviour
  deterministic.

### Relational drivers: PostgreSQL and SQLite

#### PostgreSQL reported a server statement timeout as a user cancel

- Where: `crates/sqlr-driver-postgres/src/errors.rs` (`kind_for_sqlstate`)
- Problem: SQLSTATE `57014` was always `ErrorKind::Cancelled`. That state also covers
  `statement_timeout` ("canceling statement due to statement timeout"), so a query the
  server killed on time appeared as "cancelled" in the Result, the History and the logs
  (debug level), instead of a `Timeout`.
- Test: `crates/sqlr-driver-postgres/src/errors.rs` unit test
  "server_shutdown_and_termination_are_connection_errors" (now also checks the two
  `57014` messages)
- Fix: `57014` with "statement timeout" in its message maps to `Timeout`; user and
  administrator cancels stay `Cancelled`.

#### SQLite dropped a cancel that arrived while the statement was prepared

- Where: `crates/sqlr-driver-sqlite/src/execute.rs` (`run`)
- Problem: the worker's "a statement is stepping" flag was set only immediately before
  `raw_execute`/`fetch`, so `Worker::interrupt` did nothing for a cancel arriving during
  `prepare`, the parameter-count check or the binds. The statement then ran to the end,
  while the engine still settled the Result `Cancelled` because the query's cancel flag
  was set: the user was told a statement was cancelled while its writes committed.
- Test: no deterministic seam; closing the window needs the prepare phase to be slow,
  which the fake does not model. The driver test suite passes unchanged.
- Fix: the running guard is taken before `prepare` and covers the prepare, bind and
  execute phases; it is released only while the rows result waits for fetch commands
  (where the engine does not send cancels). SQLite clears a pending interrupt when the
  next statement is prepared, so releasing the guard before the fetch wait cannot leak
  into later work.

### Relational drivers: MySQL/MariaDB, SQL Server, Oracle, ClickHouse, Snowflake, DuckDB, HANA

#### SQL Server discarded the row sets of a control-flow batch

- Where: `crates/sqlr-driver-mssql/src/execute.rs` (`returns_rows`)
- Problem: `returns_rows` only looked at the first word (plus `OUTPUT` anywhere), so a
  batch such as `IF 1 = 1 SELECT 42 AS n` or `BEGIN SELECT 1 AS n; END` went through
  `Client::execute`, which materialises the result sets and drops them, and the engine
  received `Affected(0)` instead of the rows.
- Test: `crates/sqlr-driver-mssql/src/execute.rs` unit test "only_rowsets_are_queried"
  (control-flow cases added)
- Fix: a `SELECT`/`EXEC`/`VALUES` at parenthesis depth 0 that is not the source of an
  `INSERT`/`UPDATE`/`DELETE`/`MERGE` marks the batch as returning rows. A control-flow
  batch that only writes (for example `IF @@ROWCOUNT = 0 INSERT … SELECT …`) still takes
  the row-count path.

### Document and key-value families: MongoDB, Redis, Elasticsearch

#### MongoDB `DBPointer` values were shown as `null`

- Where: `drivers/sqlr-driver-mongo/src/ejson.rs` (`from_raw`, `DbPointer`)
- Problem: the arm returned `{"$dbPointer": null}` and discarded the namespace and the
  ObjectId, so a document holding a legacy pointer lost its value; the spec says types
  sqlr does not model are *shown* (and read-only).
- Test: `drivers/sqlr-driver-mongo/src/ejson.rs`, "a_db_pointer_keeps_its_namespace_and_id"
- Fix: the raw pointer's fields are crate-private, so its Extended JSON shape is taken
  through `serde_json` (the BSON serializer special-cases the `$dbPointer` struct) and
  converted back to a `DocValue`; the document stays read-only through `unmodelled`.

#### MongoDB cancel killed every operation carrying the user's `comment`

- Where: `drivers/sqlr-driver-mongo/src/query.rs` (`tag_command`) and
  `drivers/sqlr-driver-mongo/src/write.rs` (`tagged`)
- Problem: when a statement already had a `comment`, it was reused as the cancel tag.
  Cancel finds operations by `command.comment` with `allUsers: true`, so cancelling one
  statement also stopped every other operation (another tab's, another client's) with
  that comment.
- Test: `drivers/sqlr-driver-mongo/src/query.rs`,
  "tagging_keeps_the_user_comment_but_uses_a_fresh_tag"
- Fix: the comment always gets a fresh `sqlr:<id>` suffix (the user's text is kept as a
  prefix), and the exact comment the command carries is what cancel matches.

#### Elasticsearch ignored a `size` given as a JSON string

- Where: `crates/sqlr-driver-elastic/src/query.rs` (`search`, `json_u64`)
- Problem: `"size": "5"` failed `as_u64`, so the request looked sizeless and switched to
  the point-in-time path, which removes `size` and pages through every hit. Elasticsearch
  itself coerces the string, so the user asked for 5 and got all documents.
- Test: `crates/sqlr-driver-elastic/src/query.rs`, "a_size_given_as_a_string_is_a_size"
- Fix: `size` is read from a JSON number or a numeric string, as Elasticsearch does.

#### Elasticsearch lost precision on numbers above `i64::MAX`

- Where: `crates/sqlr-driver-elastic/src/query.rs` (`json_to_doc`)
- Problem: an `unsigned_long` above `i64::MAX` fell through to `as_f64`, so
  `18446744073709551615` displayed rounded; the tabular path already kept such values as
  exact text.
- Test: `crates/sqlr-driver-elastic/src/query.rs`, "an_unsigned_long_keeps_its_digits"
- Fix: an unsigned JSON number that does not fit `i64` becomes exact text instead of a
  double.

#### Elasticsearch `_delete_by_query` with an empty query skipped the destructive warning

- Where: `crates/sqlr-core/src/es_request.rs` (`matches_all`)
- Problem: only a missing query or a `match_all` key counted as matching everything.
  `{"query": {}}` and `{"query": {"bool": {}}}` also match every document but were
  classified as a plain `Write`, so a profile that confirms destructive statements ran
  them without asking.
- Test: `crates/sqlr-core/src/es_request.rs`, "a_clauseless_query_is_a_match_all_delete"
- Fix: an empty query object, and a `bool` query whose clauses are all empty, count as
  match-all; a bool query with a real clause stays a plain write.

### Changeset apply and value encoding

#### A cancelled or refused apply cut the session's previous result short

- Where: `crates/sqlr-engine/src/apply.rs` (`run_apply`, `apply`)
- Problem: `run_apply` closed and completed the session's open stream before `apply`
  checked its cancel flag or the read-only / other-database refusals. A changeset
  cancelled while it waited for its turn, or refused, lost the previous result's
  remaining rows although none of its statements ran.
- Test: `crates/sqlr-engine/tests/apply.rs`,
  "a_cancelled_apply_does_not_cut_the_previous_result_short"
- Fix: the previous stream is taken only after the cancel flag, the read-only check and
  the other-database check, just before the first SQL the changeset runs.

#### A self-join that repeats a column was editable and wrote the wrong row

- Where: `crates/sqlr-ui/src/grid/edit.rs` (`EditBuffer::for_table`)
- Problem: editability compared only the `TableRef`, so two aliases of the same table
  looked like one table. The row key was then taken from the first result column with
  the key's name, whichever alias it came from, so editing `b.name` in
  `SELECT a.id, a.name, b.name FROM people a JOIN people b …` ran
  `UPDATE people SET name = … WHERE id = <a.id>`: the manager's row.
- Test: `crates/sqlr-ui/src/grid/edit.rs`,
  "a_self_join_that_repeats_a_column_is_read_only"
- Fix: a result that repeats one table column (same table and column twice, the only
  self-join evidence the column origins carry) is read-only with an explicit reason.

#### A self-join that does not repeat a column name is still editable (to confirm)

- Where: `crates/sqlr-core/src/chunk.rs` (`ColumnOrigin`), `crates/sqlr-ui/src/grid/edit.rs`
- Behaviour: `ColumnOrigin` holds only `{table, column}`. A self-join selecting distinct
  column names from the two aliases (`SELECT a.id, b.salary FROM people a JOIN people b
  …`) is still treated as one table, and an edit can write the wrong alias's row.
- Why it might be a bug: the same data-corruption path as the fixed case, without the
  duplicate column that now catches it.
- Why it might be intended/blocked: PostgreSQL, MySQL and SQLite result metadata carry
  the table OID/name but not the alias, so the relation instance is not available to
  detect the case; a real fix needs a spec/design decision (for example inspect the SQL
  for repeated tables, or make every result whose statement self-joins read-only).

#### `results-and-editing.md` says Apply is refused on a failed transaction (to confirm)

- Where: `docs/specs/results-and-editing.md` ("Where Apply runs") against
  `crates/sqlr-engine/src/apply.rs` and `docs/specs/query-execution.md`
- Behaviour: the code rolls the failed transaction back and applies in a new one, as
  `query-execution.md` prescribes; `results-and-editing.md` still lists a failed
  transaction among the refusals. One of the two specs is stale; this is a documentation
  decision, not a code change.

#### The changeset preview and apply disagree on a keyless default-only insert (to confirm)

- Where: `crates/sqlr-core/src/changeset.rs` (`statements`, `preview`) against
  `crates/sqlr-engine/src/apply.rs`
- Behaviour: apply passes a describe-derived column for an insert with no values, while
  the preview renders `INSERT INTO t DEFAULT VALUES`, which Oracle rejects. Not reachable
  from the grid (a grid changeset always has a row key), only through the engine API.
- Why it might be a bug: the spec says the preview shows the literals of what runs.
- Why it might be intended: the preview uses the key columns only, and keyless inserts
  are an API-only path.

### MCP server, sidecar protocol and driver SDK

#### A cancelled tool call left its MCP session busy forever

- Where: `crates/sqlr-mcp/src/server.rs` (the `tools/call` handler) and
  `crates/sqlr-mcp/src/state.rs` (`begin_call`/`end_call`, now `Inflight` and `CallGuard`)
- Problem: the in-flight counter was incremented before awaiting the tool future and
  decremented only on normal completion. If the future was dropped (client disconnect or
  aborted request, for example while a tool waits in an Approval), the count stayed at
  one, so `idle_sessions` never returned the session: its engine Agent Sessions, Results
  and tab slots were never reaped, and it kept one of the eight session slots.
- Test: `crates/sqlr-mcp/src/state.rs`, "a_dropped_call_releases_its_session"
- Fix: the count is held by a `CallGuard` whose `Drop` decrements it, so dropping the
  tool future releases the session.

#### A single row or document larger than the page budget was unreachable

- Where: `crates/sqlr-mcp/src/results.rs` (`tabular_page`, `document_page`)
- Problem: the 256 KiB budget was checked before the first item too. A value above the
  budget made the page empty with `truncated: true` at every offset, so an Agent
  advancing by the returned count looped forever.
- Test: `crates/sqlr-mcp/src/results.rs`,
  "an_oversize_row_is_still_reachable_from_the_first_page"
- Fix: the first item of a page is always included; the budget applies to the items after
  it, as the spec's "including the first item" requires.

### App flows: run and confirmations, transaction dialogs, tab switching, status bar

#### Global shortcuts bypassed open dialogs

- Where: `crates/sqlr-app/src/actions.rs` (`waits_for_modals`)
- Problem: only Apply, Discard, Refresh and Reopen closed tab waited for a modal. With an
  "Open transactions on …" prompt open, ⌘W closed the tab and replaced the pending
  disconnect/reconnect/quit action; with a "Run on …" confirmation open, ⌘W closed the tab
  but left the confirmation on screen; with the custom fetch-size dialog open, ⌘1…⌘8
  applied the size to the newly active tab.
- Test: `crates/sqlr-app/src/actions.rs`, "every_global_chord_waits_under_a_modal"
- Fix: every global chord waits while a modal layer is open; the dialog's own Esc/Enter
  remain its input.

#### A second end-transaction request replaced the pending one

- Where: `crates/sqlr-app/src/transaction.rs` (`ask_end`)
- Problem: a chord, the connection chip or a menu could call `ask_end` while an end prompt
  was already resolving; it overwrote `self.ending` and the first action (disconnect,
  reconnect, quit, close) was silently dropped.
- Test: `crates/sqlr-app/src/transaction.rs`,
  "a_second_end_request_does_not_replace_the_pending_one"
- Fix: `ask_end` does nothing while an end prompt is pending.

#### Any persistence notice abandoned a confirmed end action

- Where: `crates/sqlr-app/src/app.rs` (`failed` flag) and
  `crates/sqlr-engine/src/engine.rs`/`tx.rs` (`take_tx_failure`)
- Problem: the app treated every engine notice as a transaction failure. A history or
  settings write failing in the same frame as a confirmed "Disconnect"/"Close"/"Quit"
  cancelled the action, although only a failed commit/rollback may abandon it.
- Test: `crates/sqlr-engine/tests/tx.rs`,
  "only_a_failed_transaction_command_is_reported_as_a_failure"
- Fix: the engine records transaction-command failures separately, and the app uses that
  signal instead of "any notice".

Visual checks: the welcome screen, the demo database query, an error Result, Manual mode
with the transaction line and explorer badge, Rollback, a running query stopped with Stop,
the successful and cancelled states, closing a tab holding a clean transaction (no prompt,
as specified), and the destructive "Run on Demo" confirmation. No visual defects found.

### Transfer, dump and restore

#### The default never stopped a load after 1,000 rejected rows

- Where: `crates/sqlr-core/src/transfer.rs` (`ImportOptions::default`) and
  `crates/sqlr-engine/src/transfer/write_docs.rs`
- Problem: `max_rejected` defaulted to `None` and the app never set it, so `skip_bad_rows`
  loads kept going after 1,000 rejections while the reported rejected list was capped at
  1,000: the dialog said "rejected 1000" for thousands. The document-target path ignored
  `max_rejected` entirely.
- Test: `crates/sqlr-engine/tests/transfer_engine.rs`,
  "the_default_stops_a_load_after_one_thousand_rejected_rows"
- Fix: the default is 1,000; the document path counts every rejection and stops with the
  same "Stopped after N rejected rows" error.

#### Per-batch commits waited for more rows than the engine can hold in a batch

- Where: `crates/sqlr-engine/src/transfer/mod.rs` and `write_docs.rs` (`batch`)
- Problem: the row-per-batch option (up to 100,000) was used raw for the COMMIT boundary
  and the document batch size, while reads happen in 10,000-row chunks. A cancel after
  20,000 rows rolled back four written batches that the user expected to keep.
- Test: `crates/sqlr-engine/tests/transfer_engine.rs`,
  "per_batch_commits_never_wait_past_the_engine_batch_cap"
- Fix: the commit/document batch is clamped to 10,000 like every other batch.

#### A repeated file header produced a mapping that failed at run time

- Where: `crates/sqlr-core/src/transfer.rs` (`auto_mapping`)
- Problem: with a header such as `id,id`, both source columns were mapped to the same
  target column; the mapping screen looked valid and the transfer failed with "Column
  \"id\" is mapped twice".
- Test: `crates/sqlr-core/src/transfer.rs`, "a_repeated_source_header_maps_the_target_once"
- Fix: a target column is auto-mapped at most once; a repeated source column stays
  skipped, as an unmatched one does.

#### "Save rejected rows…" in the Import dialog writes no source values (to confirm)

- Where: `crates/sqlr-app/src/transfer_dialogs.rs` (the `save_rejected` handler) and
  `crates/sqlr-engine/src/job.rs` (`JobOutcome::Imported`)
- Behaviour: the dialog writes `line,reason` only, because the outcome carries only
  `(line, reason)`; the engine's own rejected file does include the source values.
- Why it might be a bug: the spec says the rejected CSV holds the source values, so the
  user can fix it and import it again; this file cannot.
- Why it might be intended/blocked: fixing it means carrying each rejected row's values
  through `JobOutcome::Imported` and the dialog's summary, a small API change that is
  best decided with the user.
